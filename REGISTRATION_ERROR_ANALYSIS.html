🔍 Neurosaathi Registration Flow Error Analysis

Executive Summary: The registration flow fails at the elder_profiles INSERT step with error code 42501 (permission denied / RLS policy violation). The root cause is a missing or incorrectly scoped INSERT RLS policy on public.elder_profiles.

1. Registration Flow Overview

The elder registration follows this sequence:

signInAnonymously() → profiles INSERT → saveElderProfile() → elder_profiles INSERT → FaceEnrollment → face_enrollments INSERT

If ANY step fails, the UI displays: "Account setup failed / Registration service unavailable"

Run migration 20260912_fix_anonymous_registration.sql.', detail: errMsg, }; } }
Root Cause Analysis:
⚠️ CRITICAL: The initial schema (20260910_initial_schema.sql) created permissive policies on elder_profiles:
CREATE POLICY "Manage caregiver_elder" ON public.elder_profiles FOR ALL USING (true);
This uses USING (true), which allows anyone (authenticated or anonymous) to INSERT.

However, migration 20260912_elder_profiles_unique.sql later adds a restrictive policy:

Policy: "Elder can insert own elder_profile"
Applied TO: authenticated users only
FOR INSERT TO authenticated WITH CHECK (...)
The Problem: When multiple INSERT policies exist on the same table, PostgreSQL requires ALL policies to pass (AND logic). The new restrictive policy requires:
  • TO authenticated — the user must have a valid JWT token (anonymous users have one ✓)
  • WITH CHECK — the subquery must return at least one row

The WITH CHECK condition is:

WITH CHECK ( EXISTS ( SELECT 1 FROM public.profiles p WHERE p.id = profile_id AND p.auth_user_id = auth.uid() ) );
Why it fails: The subquery joins elder_profiles.profile_id to profiles.id and checks profiles.auth_user_id = auth.uid(). Since the new elder_profiles row is not yet in the database when the INSERT is evaluated, the subquery looks up the EXISTING profiles row to verify ownership. This should succeed, but if there are conflicting policies or the policy scope is incorrectly set, it fails. Exact Error: 42501 (permission denied)

4. The Policy Conflict

Current State (from migrations):

20260910_initial_schema.sql (permissive):
CREATE POLICY "Manage caregiver_elder" ON public.elder_profiles FOR ALL USING (true);
This allows anyone to INSERT.
20260912_elder_profiles_unique.sql (restrictive):
CREATE POLICY "Elder can insert own elder_profile" ON public.elder_profiles FOR INSERT TO authenticated WITH CHECK (EXISTS (...));
This restricts to the elder's own profile only.
PostgreSQL AND logic: Both policies must allow the INSERT. The first (permissive) allows it, but the second (restrictive) requires the subquery to verify ownership.

Why the subquery might fail:

  • The profiles row exists and auth.uid() matches — should pass ✓
  • BUT: If there's a bug in the subquery or the profiles row doesn't exist, it returns 0 rows and the INSERT is denied
  • Possible root cause: profile_id is null or malformed when the INSERT is called

6. Migration SQL Required

The fix is to ensure the INSERT policy on elder_profiles is correctly scoped. If it's missing or malformed, run:

-- Drop conflicting or loose policies DROP POLICY IF EXISTS "Manage caregiver_elder" ON public.elder_profiles; DROP POLICY IF EXISTS "Elder can insert own elder_profile" ON public.elder_profiles; -- Create a single, clear INSERT policy that allows authenticated users -- to insert their own elder profile CREATE POLICY "Elder can insert own elder_profile" ON public.elder_profiles FOR INSERT TO authenticated WITH CHECK ( EXISTS ( SELECT 1 FROM public.profiles p WHERE p.id = profile_id AND p.auth_user_id = auth.uid() ) ); -- Verify the policy was created SELECT tablename, policyname, cmd, qual FROM pg_policies WHERE tablename = 'elder_profiles' ORDER BY policyname;
📝 This SQL is already in 20260912_elder_profiles_unique.sql — ensure it was run in the Supabase SQL editor.
